# 2026-09-23 工作日志

## 新项目：安卓端背单词 / 背课文系统（需求碰撞阶段）

**需求概要**
- Web 管理端：按「年级 → 学期 → 单元」导入英语单词（含短语、句子）与语文课文，导入格式 Excel / Word。
- 安卓学生端：① 背英语——出中文→语音说英文→逐个念字母（教室 → class → c-l-a-s-s）；或出英文→答中文。② 背语文课文——逐字提示式背诵（背到哪个字，哪个字才显示）。
- 记录：题目、答案、对错、用时，供后续重复练习与分析；默认不限时，可设置限时。
- 部署：服务器在局域网内的一台电脑上。

**已向姚工提出的关键分叉点（待确认）**
1. 语音识别引擎位置：本地 Whisper（内网可用、吃算力） vs 云 API（准但需外网） vs 安卓端离线。
2. 单字母拼读识别率低：b/d/e/g/p/t/v/z 易混，纯语音判分误判率高，建议单词用语音、字母用键盘或混合。
3. 语文「背到哪显示到哪」= 流式识别 + 原文逐字对齐，需容忍漏字/回读，或改用半自动推进。
4. 浏览器在 `http://局域网IP` 下麦克风权限被拒 → 需原生 App 或自签 HTTPS。
5. 离线可用（本地缓存 + 离线答题队列）、服务器发现（SERVER_IP 会变）、单机数据备份。
6. 答题记录字段需提前预留（识别置信度、首次是否答对、提示/重试次数、模式），否则 SRS 与分析算不出来。
7. 限时到点后的处理规则（判错 / 跳过 / 标记超时）、倒计时起点。
8. 使用规模：自家 1-2 个孩子 vs 一个班几十人（影响账号体系与架构）。

## 选型结论（已与姚工确认）

| 层级 | 选型 |
|---|---|
| 学生端 | Flutter（手机 + 平板） |
| 管理端 = 老师端 | Web 页面，老师负责录入 + 看学生数据 |
| 后端 | FastAPI + uvicorn |
| 数据库 | PostgreSQL（或 SQLite + WAL） |
| 语音识别 | 阿里云 / 火山引擎实时流式 ASR，**只取文本，不做发音评分** |
| 登录 | 学号 + 弱口令，老师端可批量重置 |
| 部署 | 局域网 Windows 电脑 + 固定内网 IP |

**使用规模**：一个班（几十名学生）。

**关键调研发现（2026-09 实地查证）**
1. 火山引擎豆包大模型流式语音识别**仅对已认证企业用户开放**，个人主体可能走不通，需先确认资质。
2. 阿里云**推荐 Paraformer 实时版 / Fun-ASR 实时版**：双向流式（边说话边出字），支持 `language_hints` 按题目切语种（英语题 en / 语文题 zh）。注意老版「智能语音交互」语种绑在项目模型上、无法用参数指定，选型时别踩。
3. **中文 ASR 识别英文单词会翻车**（class 可能变「克拉斯」），必须按题目类型切语种。
4. **定制热词**是关键提准确手段：把当前单元单词表、课文原句、A~Z 谐音（see/ell/艾尔）作为热词前置到引擎层。
5. 音频要求：单声道 16bit、8k/16k 采样率，PCM/WAV/OPUS 等；`enable_intermediate_result` 返回中间结果，是逐字点亮的基础。
6. **架构决策：App 不直连云 ASR，走局域网服务器中转**（WebSocket）。理由：AccessKey 不下发到 APK（防反编译刷量）、可换厂商、可统一做限流/成本统计/降级。

**已向姚工补充的设计澄清**
- 「手动提示」= 卡壳出口，三档强度（显示剩余字数 / 给首字提示 / 直接显示答案），主动按钮 + 静音超时自动降档双通道，每次提示计入成绩。
- 「多字母组合念」：识别结果归一化为纯字母序列比对，`c-l-a-s-s` / `cla-ss` / `class` 均可判对；需维护 A~Z 中英谐音映射表；键盘输入入口常驻界面做兜底。

### 二、两个真 bug（不修的话生产上会炸）

**1. `X-Trace-Id` 响应头从来没被加上**
`TraceIdMiddleware` 只是原样 `await self.app(...)`，**压根没包装 `send`**。但 CORS 里写了 `expose_headers=["X-Trace-Id"]`、错误处理器里也在设这个头 → 说明本来就该有。
→ 补 `send_with_trace_id`：在 `http.response.start` 时追加该头；业务侧已显式设置则不重复添加。

**2. 10006 响应体里的 `trace_id` 是空串（U6 抓到的）**
FastAPI 中间件栈是 `ServerErrorMiddleware(最外) → …用户中间件… → ExceptionMiddleware(最内)`，而注册在 `Exception` 上的全局处理器**是由 ServerErrorMiddleware 调用的** —— 它在 `TraceIdMiddleware` **之外**。异常穿出 TraceIdMiddleware 时 `finally` 已经把 contextvars reset 掉了，处理器拿到的自然是空串。
→ **`trace_id` 除写 contextvars 外，再写一份进 `scope`**（`scope` 是同一个 dict 对象、被逐层原样透传，能活着到达最外层）。新增 `trace_context_from_scope()` 上下文管理器，错误处理器用 `with` 包住即可 —— `ok()` / `fail()` / `get_trace_id()` **一行都不用改**。

### 三、真机启动烟测：`backend/scripts/smoke_boot.py`（12/12）

### 踩坑记录（重要）

1. **Node 22 内置 `WebSocket`（undici）与 Edge 的 CDP 完全不通帧** —— 握手成功（`open` 触发、`readyState=1`），但**一个回帧都没有**，`Page.enable` 超时。实测连 vite 自己的 WS 服务端也是 **0 帧 + error**，所以是 undici WS 自身的问题，与 CDP 无关。项目也没有 `ws` 依赖、且不该为一个验收脚本去动 `package.json`。
   → **改用 Chrome 官方的 `--remote-debugging-pipe`**：fd3 = 我们写、fd4 = 我们读，消息是「一行 JSON + 一个 NUL 字节」。`Target.createTarget` + `Target.attachToTarget{flatten:true}` 拿 `sessionId`，之后每条命令带上它。实测 createTarget / attach / evaluate / Page.enable 全通。
2. **两处失败其实是我的断言写错了**，不是产品缺陷：顶部栏文案走 store 的 `displayName = real_name || username`，而初始管理员 `real_name` 就是「管理者」（`main.py::_ensure_admin_account`），所以期望值应是「管理者」而非 `admin`。改成按 `displayName` 语义断言，并单独加一条显式断言把这个行为钉住。
