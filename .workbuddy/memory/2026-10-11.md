## en2zh「没听清」真机排障（20:45，第二批修复）
根因三层叠加：
1. `_STREAMING_TASKS` 只有 recite → spell_en2zh 走非流式批量，103s 音频攒到 end 撞 3s 超时（connect_timeout_ms 被复用当总超时）；
2. WorkBuddy 会话注入 HTTP_PROXY/HTTPS_PROXY 慢代理 → dashscope HTTP 过代理必挂（OCR 502 同源坑第二次踩）；
3. 网关对未 start 的音频帧每帧回 10001 abort → App 常驻录音器 end 后仍推帧，被刷成「没听清」死页。
修复（session_manager.py / aliyun_provider.py / fallback.py / arbitrator.py）：
- en2zh start 改走 recite 流式通道（zh2en 仍批量）；`_finish_http` 超时改用 batch_timeout_ms（默认 30s）；
- 全部 httpx.AsyncClient 加 trust_env=False（局域网应用不吃系统代理，一劳永逸）；
- handle_bytes 未 start 帧**静默丢弃**（每轮只 log 一次，`_orphan_frames` 限流），不再回 error；
- 后端启动必须 `env -u HTTP_PROXY -u HTTPS_PROXY`（本次重启已带）。
测试：test_audio_before_start_rejected 断言翻新（error→静默）；pytest 279 passed。客户端零改动、免重打 APK。

## 「连接断开+无法识别」真凶（21:30，第三批修复）——autoDispose 单例陷阱
证据链（日志+DB+logcat，非猜测）：
- 服务端两轮全对：partial×3 + final 正常下发、asr_logs status=ok task=recite（切流式生效）、answer 不落库（内存态）故 DB 无记录≠没发；
- WS 12:56 连上后 13:07:44 被 App 用 1000 码关（服务端三种主动关闭路径都没打日志→websocket.disconnect，即客户端先关）；随后新连接+第二轮，13:08:18 又关；
- logcat 无崩溃、无页面退出（仅 21:08 拉了通知栏）。
根因：`wsClientProvider` 是 **autoDispose** 且 `onDispose(client.dispose)`（关 WS+关消息/状态流），spell_page 用 `ref.read`（不 keep alive）→ riverpod 回收后页面变成聋子：final 收不到→`_waitForFinal` 超时弹「没听清你说的话」（最早的主诉）；states 关闭前最后事件是 closed→「连接断开了」横幅常驻；重开 begin 连新 socket 但消息流已死→「服务端全对、页面永远收不到判定」。
修复：spell_page 自建 WsClient（serverStore/localStore 用 ref.read 取实例），与 session 同生命周期；wsClientProvider 保留但不再被 spell_page 使用。
教训：**长生命周期会话对象不能包在 autoDispose provider 的实例外面**；riverpod 3 里 read 不保活。
验证：flutter analyze 干净、spell 10 tests + 全量 274 passed；重打 APK 装机。
