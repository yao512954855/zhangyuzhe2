> **一句话结论先行**：本产品的核心是**语音交互**。拼读环节到底能判多严、谐音表要做多大、要不要上多模态仲裁——**这三个问题只能靠实测数据回答**。本方案就是把这笔数据拿到手，并且**在开测之前先把判定门限定死**，避免结果出来后「事后找理由」。

---

## 1. 为什么必须做（以及不做会怎样）

拼读环节的设计里有一堆**拍脑袋定的参数**：

- 相似度阈值 0.85；
- `fuzzy` 的触发条件「长度 ≥6 且仅 1 处差异」；
- 谐音映射表要覆盖到什么程度（只覆盖英文字母名？还是含中文腔谐音？）；
- 第几次失败才降级键盘。

这些参数全部建立在一个**未经验证的假设**上：云 ASR 能稳定识别出「孤立字母 + 非词字母组合」的发音。

**这个假设很可能是错的。** 业界经验：清辅音（`l` `s` `t`）在孤立念读时几乎没有能量；`b/d/e/g/p/t/v/z` 这一组在识别里长期互相混淆。如果实测出来字母序列准确率只有 60%，那 §6.2 的整套判分规则就得改，而不是硬套。

**后果对比**：

| 做预研 | 不做预研 |
|---|---|
| 半天到一天，拿到真实数据，参数有依据 | 开发完才发现判不准，返工重做判分 + 前端交互 |
| 提前决定是否需要多模态仲裁，避免后续改判分主链路 | 上线后天天收「我念对了但判我错」的投诉 |
| 谐音表的规模有数据支撑，不做无用功也不漏 | 家长对系统失去信任，孩子不愿用 |

## 2. 判定门限（**开测前先定死**）

> 门限是**决策依据**，不是结论。先定门限，再看数据，避免「数据出来后按情绪调标准」。

| 指标 | 达标门限 | 说明 |
|---|---|---|
| **整词识别率** | ≥ 95% | 归一化后完全一致的占比。说词环节的判分基线 |
| **字母序列准确率** | ≥ 85% | 经谐音表转换后与目标字母序列一致的占比。**这是最关键的一项** |
| **空结果率** | ≤ 5% | 返回空文本的占比。高的话说明音频链路或格式有问题 |
| **首字延迟（P95）** | ≤ 800 ms | 语文逐字点亮依赖它；超过则点亮会有明显滞后感 |
| **最终结果延迟（P95）** | ≤ 1.5 s | 说词/拼读判定的等待时间上限 |

**分档结论**：

| 字母序列准确率 | 定性 | 后续动作 |
|---|---|---|
| ≥ 85% | 达标 | 按 §6.2 现状执行；多模态保持预留（二期） |
| 50% – 85% | 勉强 | ① 扩谐音表 ② 放宽 `fuzzy` ③ 屏幕加切分引导 ④ **评估启用多模态仲裁**；键盘降级阈值提前到第 2 次失败（仍属降级） |
| < 50% | 不达标 | **多模态仲裁提前到一期**（拼读的第二判据）+ 扩谐音表 + 强化切分引导。**不得改为键盘为主**（需求 §9.8 前提约束） |

## 3. 测试集设计

### 3.1 选词（25 个，覆盖六类难点）

| 类别 | 词例 | 考察点 |
|---|---|---|
| 短词（3–4） | `cat`、`dog`、`pen`、`bus` | 短音频，信息量少，易受噪声影响 |
| 中词（5–7） | `class`、`apple`、`teacher`、`student` | 主流程高频词 |
| 长词（8+） | `classroom`、`restaurant`、`beautiful` | 逐字母念读时长较长，易漂移 |
| 清辅音密集 | `class`、`little`、`apple` | `l` `s` `t` 孤立念读的识别 |
| 易混字母密集 | `bed`、`red`、`bag`、`dog` | `b/d/e/g/p/t` 混淆组 |
| 短语 / 句子 | `a classroom`、`Our classroom is big.` | 词间连读、句尾清辅音 |

### 3.2 念法（每个词录三种）

| 类型 | 示例 | 目的 |
|---|---|---|
| 整词 | `class` | 说词环节 |
| 逐字母 | `c - l - a - s - s` | **核心考察：孤立字母识别** |
| 音节切分 | `cla - ss` | 非词字母组合，最容易失败。**第一批已证实：22 条样本无一正确，此路已废**（报告 §3.1） |

### 3.3 样本

- **人数**：3–5 人，覆盖小学低年级（1–3）、高年级（4–6）、初中（7–9）各至少 1 人。
- **优先**真实学生录音；拿不到就用成人**模仿儿童口音**（语速偏慢、发音不标准），并在报告中**明确标注**，结论打折扣使用。
- **条数估算**：25 词 × 3 念法 × 4 人 ≈ **300 条**。够用，也不至于测到崩溃。

### 3.4 录音环境

- 至少两种：**安静室内** + **有背景噪声**（模拟教室/客厅）。
- 设备至少两种：手机自带麦 + 有线/蓝牙耳麦（真实使用场景里两者都存在）。
- 统一 16kHz / 单声道 / 16bit / PCM（与生产一致，格式不符结论作废）。

## 4. 对比维度（矩阵）

| 维度 | 取值 | 目的 |
|---|---|---|
| 厂商 | 阿里 / 火山 | 选型依据 |
| 模型 | 通用实时 / 教育专用（若账号可用） | 教育模型是否真有优势 |
| 热词 | 开 / 关 | 验证「把当前单元词 + A–Z 谐音塞进热词」的收益 |
| 语种提示 | `en`（说词/拼读） / 误设 `zh`（对照组） | ~~验证「中文模型识别英文会翻车」的假设~~ **❌ 该假设已被第一批实测推翻：拼读场景 `zh` 反而更准（85%→95%）。原对照设计本身有误，第二批请按「`word` 用 `en` / `spell` 用 `zh`」重新设计对照** |
| 音频来源 | 安静 / 噪声；手机麦 / 耳麦 | 环境鲁棒性 |

**不是所有组合都要跑全**。推荐两轮：

- **第一轮（摸底，约半天）**：阿里通用模型，热词关，安静环境，3 人样本。**只为拿到基线数字**。若基线已达标 → 直接收工。
- **第二轮（优化，约半天，仅在第一轮不达标时做）**：加开热词、加噪声环境、加教育模型、加火山对照；**同时跑多模态对照**（见 §6）。

## 5. 执行方法

### 5.1 流程

1. **准备音频**：按 §3 录制，命名规范 `{人数编号}_{词}_{念法}_{环境}.wav`，例如 `S1_class_spell_quiet.wav`。
2. **跑识别**：用一段离线脚本，复用 `backend/app/services/asr/aliyun_provider.py`（**这门脚本是 BE-06 的副产物，先做它能顺带把 Provider 调通**），把音频喂进去，导出识别文本。
3. **人工标注**：把识别文本与目标对照，逐条标注 `正确 / 部分正确 / 错误 / 空`。
4. **算指标**：按 §2 的门限口径统计，产出数据表。
5. **出结论**：按 §2 分档，给出设计建议。

### 5.2 脚本骨架

```python

AUDIO_DIR = pathlib.Path("qa/audio")

async def run_one(provider, wav: pathlib.Path, lang: str, hotwords: list[str]):
    """单条音频 → 识别文本 → 延迟。"""
    ...

async def main():
    factory = ASRFactory.from_config("asr.yaml")
    judge = JudgeService()
    rows = []
    for wav in sorted(AUDIO_DIR.glob("*.wav")):
        meta = parse_name(wav.name)              # 解析出 词 / 念法 / 环境
        text, latency_ms = await run_one(factory.primary(), wav, lang="en", hotwords=[])
        if meta["mode"] == "spell":
            norm = judge.normalize_spell(text)   # 谐音表 → 纯字母序列

            correct = judge.normalize_text(text or "") == meta["word"]

                     "correct": correct, "latency_ms": latency_ms})

    summarize(rows)   # 输出各维度指标

asyncio.run(main())
```

> 说明：脚本放在 `qa/`，**不进 `backend/app/`**，属于一次性工具。但 Provider 与谐音表**必须复用生产代码**，否则测出来的数字跟线上不是一回事。

### 5.3 注意事项

- **不要把 `expected` 传给云厂商**（与生产一致，见契约 §6.3 安全红线）。
- 每条音频多跑 2–3 次，观察**结果稳定性**（同一段音频返回不一致，本身就是重要发现）。
- 记录**原始返回文本**，不要只记「对/错」——后续扩谐音表时这些原始文本是唯一依据。

## 6. 多模态对照（仅在 ASR 不达标时执行）

如果 §2 判定为「勉强」或「不达标」，**当场**补一组多模态对照，不要把问题留到开发后：

- 取**识别失败的那批音频**（约 30–50 条），交给多模态模型；
- 提问方式固定，降低输出波动：
  > 「这段音频里，说话人依次念出了哪些英文字母？只输出字母序列，不要其他内容。」
- 统计多模态在同一批样本上的**字母序列准确率**，与专用 ASR 对比。

**决策规则**：

| 对照结果 | 决策 |
|---|---|
| 多模态准确率显著更高（≥ 20 个百分点） | **一期启用 `ArbitratorProvider`**（BE-06 F19 已有接口位，只需补实现） |
| 两者都不行 | 回到交互层：屏幕**固定切分引导**（`c｜l｜a｜s｜s`）+ 扩谐音表 + 放宽 `fuzzy`；**仍不退回键盘为主** |
| 多模态更差 / 成本不可接受 | 维持专用 ASR，只做谐音表扩容与阈值放宽 |

> 注意多模态的**延迟**（秒级）与**成本**（按 token）：它**只做仲裁**（占比应当很小），绝不能进实时逐字点亮链路。
